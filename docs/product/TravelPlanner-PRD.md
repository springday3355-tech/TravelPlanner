# TravelPlanner (트래블메이커) — PRD

> 개발 에이전트용 요구사항 문서. "무엇을 만드는지 · 무엇은 아직 범위 밖인지"를 판단하는 기준으로 쓴다.
> 기술적 구현 규칙은 이 문서가 아니라 `docs/architecture/TravelPlanner-SA.md`를 따른다.

- 버전: 0.1 (기획서 원문 기반 초안)
- 출처: 사용자가 채팅으로 전달한 "실시간 아이디어(가명: 트래블메이커)" 기획서 원문
- 상태: 0단계 안정화와 1단계 기본 CRUD 완료, 여행 계획 최소 흐름 설계 예정

## 1. 한 줄 목표

사용자가 조건(기간/예산/취향/동행)만 말하면 AI가 여행 일정을 자동 생성하고, 실시간으로 수정·공동 편집까지 가능한 여행 플래너.

## 2. 문제 정의

- 여행 일정을 짤 때 장소 검색, 동선 계산, 영업시간 확인을 사람이 수작업으로 조합해야 한다.
- 동행자와 함께 일정을 짤 때 실시간으로 반영이 안 되어 메신저/문서로 따로 공유하고 수동 병합해야 한다.

## 3. 타겟 사용자

- 여행을 계획하는 개인/그룹 사용자. 특히 동행자와 함께 일정을 조율해야 하는 그룹 여행 사용자.

## 4. 핵심 시나리오

1. 사용자가 도시/날짜/예산/취향을 입력한다.
2. AI가 장소를 추천하고 이동 동선·영업시간을 고려해 일정 초안을 만든다.
3. 사용자가 채팅으로 "비 오면 실내 코스로 변경" 같은 수정 요청을 하면 일정이 즉시 갱신된다.
4. 사용자가 동행자를 초대하면, 동행자도 같은 일정을 실시간으로 보고 동시에 편집할 수 있다.

## 5. 도메인별 기능 범위

### 5.1 회원/로그인 (auth) — 1단계 [구현 완료]
- 회원가입, 로그인(JWT), 세션/토큰 관리.
- **범위 밖(1단계)**: 소셜 로그인, 이메일 인증, 비밀번호 찾기 — 필요 시 별도 이슈로 분리.

### 5.2 일정 (itinerary) — 1단계 [구현 완료]
- 여행 조건 입력 → 일정 초안 생성/저장/수정, 일자/방문 항목/동행자 관리, 공유 링크 생성.
- **범위 밖(1단계)**: AI 자동 생성 로직 자체(외부 LLM 연동)는 2단계, 지금은 CRUD만.

### 5.3 장소/검색 (place) — 1단계 (기본 CRUD) [구현 완료], 이후 검색 고도화
- 1단계: 장소(POI) 정보의 기본 CRUD, 지역/카테고리 기준 단순 필터링(JPA 쿼리).
- 여행 계획 흐름에서 필요한 장소 데이터와 검색 품질을 확인한 뒤 Elasticsearch/Meilisearch 도입 여부를 결정한다.

### 5.4 실시간/채팅 (realtime) — 여행 계획 흐름 검증 이후
- WebSocket 기반 수정 요청 송수신, AI 일정 생성 진행률(%) 스트리밍, 동행자 화면 실시간 동기화.
- **1단계에서는 착수하지 않는다.** (`docs/architecture/TravelPlanner-SA.md` 7절 순서 참고)

## 6. 차별화 기능 (기획서 원문)

동행자 실시간 공동 편집 및 일정 생성 상태 스트리밍: 한 사용자가 일정을 수정하면 동행자 화면에 새로고침 없이 즉시 반영되고, AI 일정 생성 진행률이 실시간 공유되는 공동 작업 공간.

## 7. 비기능 요구사항 / 기술 주제 (기획서 원문 기반)

| 항목 | 내용 | 적용 단계 |
|---|---|---|
| 검색엔진 인덱싱 | 형태소 분석, 동의어/가중치 튜닝 기반 장소 랭킹 검색 | 데이터량·검색 품질 확인 후 |
| Redis 캐싱 | 인기 검색어, 장소 상세, 생성 중 일정 초안 캐싱 | 병목·공유 상태 확인 후 |
| 동시성 제어 | 낙관적 락(버전 관리) + 필요 시 분산 락 | 공동 편집 도입 시 |
| WebSocket | 양방향 실시간 통신 | 기본 여행 계획 흐름 검증 후 |

## 8. 성공 기준 (제안 — 확정 필요)

- [ ] 조건 입력→일정 생성까지의 소요 시간
- [ ] 동행자 동시 편집 시 데이터 유실률 0%
- [ ] 검색 응답 지연 목표치

> 위 지표는 기획서에 수치가 명시되어 있지 않아 임의로 채우지 않았다. 확정되면 이 절을 갱신한다.

## 9. 알려진 제약/리스크 (기획서 원문)

- 양방향 실시간 동기화, 다중 서버 소켓 확장(Redis Pub/Sub), 동시성 예외 처리로 개발 난이도 상승.
- MySQL(마스터)과 검색엔진 인덱스 간 동기화 일관성 보장의 어려움.
- Elasticsearch/Redis 인프라 + 외부 AI API 호출에 따른 운영 비용 증가.
