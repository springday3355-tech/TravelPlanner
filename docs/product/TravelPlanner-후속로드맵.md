각 단계는 앞 단계가 `main`에 병합된 뒤 시작한다. 이렇게 하면 문제가 생겼을 때 변경 범위와 원인을 단계 단위로 확인할 수 있다.

## 3단계: 실제 장소 데이터 연동 [완료]

목표: 사용자가 입력한 도시와 취향으로 Google Places의 실제 장소를 검색하고 내부 장소 데이터로 가져온다.

- `PlaceProvider` 인터페이스와 Google Places 구현체 추가
- Text Search와 Place Details 연동
- 외부 장소 ID, 출처, 마지막 동기화 시각 저장
- 요일별·자정 이후 영업시간 모델 추가
- Google 유형을 내부 카테고리로 변환
- 중복 적재 방지, 타임아웃, 재시도, 호출량 제한 처리
- API 키 환경변수와 예제 설정 추가
- 공급자 응답 계약 테스트와 장애 시 기존 장소 사용 테스트

완료 기준: 실제 도시 검색 결과로 일정 초안을 만들 수 있고, 키가 없거나 외부 API가 실패해도 오류 응답 또는 기존 데이터 사용이 예측 가능해야 한다.

구현 결과는 `docs/product/TravelPlanner-3단계-완료보고.md`에 기록한다.

## 4단계: 실제 이동 경로와 일정 품질 개선 [완료]

목표: 직선거리와 평균 속도 추정을 실제 도로망·교통수단별 이동시간으로 교체한다.

- 경로 공급자 인터페이스 추가
- 도보·자동차·대중교통 정책 결정 및 연동
- 출발지와 장소 간 이동시간 행렬 계산
- 영업시간, 이동시간, 체류시간 충돌 재배치
- 외부 경로 호출 캐시와 비용 상한 적용
- 기존 Haversine 계산을 장애 시 대체 경로로 유지

완료 기준: 같은 입력에서 이동 불가능한 일정을 만들지 않고, 외부 경로 장애 시에도 일정 생성이 가능해야 한다.

구현 결과는 `docs/product/TravelPlanner-4단계-완료보고.md`에 기록한다.

## 5단계: 대화형 AI 일정 수정

목표: “비 오면 실내 코스로 변경” 같은 자연어 요청을 검증 가능한 명령으로 바꿔 일정을 수정한다.

- LLM 공급자와 구조화 출력 형식 선정
- 자연어를 일정 변경 명령으로 변환
- 권한·날짜·영업시간·예산 검증 후 적용
- 변경 전후 차이와 실패 이유 반환
- 프롬프트 버전 관리, 대표 시나리오 평가, 비용 제한
- 잘못된 응답이 DB 변경으로 이어지지 않도록 트랜잭션 경계 설정

완료 기준: 대표 수정 시나리오가 구조화된 명령으로 안정적으로 변환되고, 검증 실패 시 원래 일정이 보존되어야 한다.

## 6단계: 운영 데이터베이스와 배포 기반

목표: 로컬 개발 구성을 운영 가능한 MySQL 기반으로 전환한다.

- MySQL 프로필과 연결 설정
- Flyway 스키마 마이그레이션 도입
- 비밀값 관리와 환경별 설정 분리
- Docker 기반 실행 환경과 상태 확인 구성
- 백업·복구 절차와 로그 정책 작성
- CI에 MySQL 통합 테스트 추가

완료 기준: 빈 데이터베이스에서 마이그레이션만으로 기동되고, 배포 환경에서 비밀값이 코드나 로그에 노출되지 않아야 한다.

## 7단계: 공동 편집과 동시성 제어

목표: 동행자가 같은 일정을 보고 수정 결과를 실시간으로 공유한다.

- 일정 버전과 낙관적 락 추가
- WebSocket 인증과 일정별 구독 권한 적용
- 수정 이벤트와 생성 진행률 전송
- 충돌 응답과 재시도 UX에 필요한 계약 정의
- 다중 서버가 필요해질 때 Redis Pub/Sub 도입

완료 기준: 두 사용자의 동시 수정에서 조용한 데이터 덮어쓰기가 발생하지 않고, 권한 없는 사용자가 이벤트를 구독할 수 없어야 한다.

## 8단계: 검색과 캐시 고도화 판단

목표: 실제 사용 지표로 검색엔진과 Redis 도입 필요성을 결정한다.

- 장소 수, 검색 정확도, 응답시간, 반복 호출률 측정
- JPA 검색 기준선을 먼저 기록
- 형태소·동의어·거리 가중치가 필요한 경우 검색엔진 비교
- 반복 조회나 외부 API 병목이 확인된 경로만 캐시
- 캐시 무효화와 DB·검색 인덱스 동기화 정책 수립

완료 기준: 측정값과 목표치로 도입 여부를 결정하고, 도입한다면 장애·불일치 처리까지 검증해야 한다.
