# 트래블메이커 — 비즈니스 정책 정리본

> 도메인 로직(Service 계층)을 구현할 때 따라야 할 비즈니스 규칙. 기술 구현 방법은 이 문서가 아니라
> `docs/architecture/TravelPlanner-SA.md`를 따른다. 이 문서에 없는 규칙을 임의로 만들지 말고,
> 없으면 "결정 대기"로 남기고 사람에게 확인한다.

## 1. 회원 (auth)

- 이메일은 유일해야 한다 — 중복 가입 시 `BusinessException(ErrorCode.MEMBER_EMAIL_DUPLICATE)`(M001)로 거부. **구현 완료.**
- [x] ~~인증 방식~~ → JWT(STATELESS)로 확정. `POST /api/auth/login` 성공 시 accessToken 발급 (`docs/architecture/TravelPlanner-SA.md` 5.4절).
- [ ] 회원가입 시 이메일 인증 필요 여부 — 결정 대기 (PRD 5.1절: 1단계 범위 밖으로 잠정 제외)
- [ ] 비밀번호 정책(길이/조합 규칙) — 정식 결정 대기. 코드에는 최소 8자라는 잠정 기본값만 적용되어 있다(`auth/dto/SignupRequest.java`) — 정책으로 확정된 것은 아니다.
- [ ] 회원 탈퇴 시 본인 소유 일정(itinerary) 처리 방식 — 즉시 삭제 / 소유권 이전 / 보관 중 결정 대기. 결정 전까지 탈퇴 기능 구현하지 않는다(미구현 상태 유지).

## 2. 일정 (itinerary)

- 일정 소유자(owner)만 일정을 삭제할 수 있다.
- 동행자(participant)의 역할은 `OWNER` / `EDITOR` / `VIEWER` 세 가지다.
  - `EDITOR`: 일정 내용 수정 가능, 동행자 초대/삭제 불가.
  - `VIEWER`: 조회만 가능.
  - `OWNER`: 모든 권한 (양도 정책은 결정 대기).
- 동행자 초대 시 부여 가능한 역할은 `EDITOR`와 `VIEWER`뿐이다. `OWNER`는 별도의 소유권 이전 정책이 확정되기 전까지 초대로 부여하지 않는다.
- 기존 `OWNER` 참여 정보는 삭제할 수 없다.
- 종료일은 시작일보다 빠를 수 없고, 일정 일자의 날짜와 순서는 여행 기간과 일치해야 한다.
- 같은 일자의 방문 순서는 중복될 수 없으며 종료 시간은 시작 시간보다 늦어야 한다.
- 공유 링크(`share_token`)로 접근한 사용자는 기본적으로 `VIEWER` 권한으로 간주한다. 링크로 EDITOR 권한을 부여할지는 결정 대기.
- [ ] 동시 편집 충돌 시 처리 방식 — 3단계(낙관적 락) 도입 전까지는 "마지막 저장이 이긴다"(last-write-wins)로 잠정 동작. 데이터 유실 리스크가 있음을 PRD/SA 문서에 명시했으므로, 3단계 전까지 이 정책을 사람에게 재확인 없이 강화하지 않는다(과도한 락 로직을 임의로 넣지 않는다).
- [ ] 일정 삭제 시 하위 데이터(itinerary_day, itinerary_item) 처리 — cascade delete 가정. 소프트 삭제 요구 시 별도 결정 필요.

## 3. 장소 (place)

- 장소 데이터의 출처(내부 등록 vs 외부 API 수집)는 1단계에서는 관리자/내부 등록만 가정한다.
- [ ] 사용자가 직접 장소를 등록할 수 있는지, 등록/수정/삭제를 ADMIN으로 제한할지 — 결정 대기 (기획서에 명시 없음). **현재 구현은 "인증된 사용자면 누구나 가능"** — 결정 대기 항목을 임의로 제한하지 않기 위한 잠정 상태이며, ADMIN 제한이 아니다. 정책이 확정되면 `common/config/SecurityConfig.java`와 `PlaceController`에 역할 검사를 추가한다.
- 카테고리 값의 허용 목록(FOOD/CAFE/SIGHT/ACCOMMODATION 등)은 `TravelPlanner-DB설계.md` 2.6절 기준을 따른다. 목록을 늘릴 때는 이 문서와 DB 설계 문서를 함께 갱신한다.
- 일정 항목에서 사용 중인 장소는 삭제하지 않는다. 일정에서 해당 장소를 먼저 제거한 뒤 삭제한다.

## 4. 에러/응답 정책

- 모든 실패 응답은 `common/exception/ErrorCode`에 정의된 코드만 사용한다. 정책 문서에 없는 새 실패 케이스가 생기면, 그 케이스를 이 문서에 먼저 추가하고 `ErrorCode`에 반영한다.
- 사용자에게 노출되는 에러 메시지는 내부 구현(SQL, 스택트레이스 등)을 포함하지 않는다.
